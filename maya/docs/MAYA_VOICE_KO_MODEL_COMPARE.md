## 2. 확정된 결론

1. **로컬 "소형" 모델로는 안 된다.** 형식이 맞으면(qwen2.5-coder) 사실을 1건만 뽑아 9개 중 3개,
   품질이 맞으면(llama3.1:8b) 5분이 넘는다. 대화 파이프라인의 추출 단계에 넣을 수 있는 조합이 없다.
2. **프롬프트 언어 규칙은 원인이 아니었다.** `use_input_language=True` 로 강제하고 345자짜리
   최소 프롬프트로도 gemma3:4b 는 짧은 경우 한국어, 긴 경우 **중국어**로 갈렸다 → 모델 능력 문제.
3. **qwen3 계열은 기본값으로 쓰면 안 된다.** 사고 토큰이 `max_tokens` 예산을 먹어 JSON 이 안 닫힌다.

## 3. EXAONE-4.0-1.2B(Q8 GGUF) — 왜 실패했는지까지 기록

"한국어 특화 1.2B"라 후보 1순위였고, 실제로 받아서 ollama 에 올렸다. 결과:

- 무한 사고: EXAONE-4 는 **기본이 사고 모드**다(chat_template 이 `enable_thinking` 을 요구).
  ollama 의 OpenAI 호환 엔드포인트는 `chat_template_kwargs`/`think` 를 **무시**하고
  `options` 만 존중한다 → 사고를 끌 방법이 없어 60s timeout, `max_tokens=200` 에서 `finish=length`.
- 그나마 나온 응답이 **프롬프트의 JSON 예시를 그대로 복사**(`text: "<사실>"`)했다. 345자 프롬프트에서도.
- 가중치 손상은 아니다: `integration/gguf_weight_check.py` 로 확인 → 333개 텐서 중 표본에서
  **NaN/Inf 0.00%, Q8_0 scale 범위 정상**(예: token_embd scale max 2.0e-3) → **판정: 불량 의심 없음**.
  즉 실패 원인은 100% **서빙 경로(ollama)의 사고 모드 제어 부재**다.

**재시도 조건**: vLLM(`chat_template_kwargs={"enable_thinking": false}`)이나 transformers 로
서빙할 때. ollama 경로에서는 **같은 실패가 반복된다**(같은 함정을 두 번 밟지 않기 위해 기록).

## 5. 권고

- **당장**: 운영은 `vm_ko_raw_memory.py` 경로(원문 저장 + E5 검색, top1 4/4)로 간다.
  추출은 "되면 좋고 안 되면 원문" 으로 두고 대화 지연에 넣지 않는다.
